# 04b — Replication, serialization and safe execution contract

Status: **proposed normative companion to 04, 17 Oct 2026; not implemented or independently approved**. Corrections address review F1–F9. User approval authorizes corrections, not invented Dynamo behavior. MUST means a requirement for a future implementation, not an assertion that it exists.

## 1. Scope and evidence boundary

This is an **OpenBIM** format/runtime contract informed by Dynamo, not `.dyn` import, DesignScript compatibility, or complete Dynamo equivalence. The examined Dynamo source snapshot is `8a211c5f306e5b54541fa57081aa1ffa32a65e90` (retrieved 17 Oct 2026 from master; not asserted to be a released 4.x build). Source references below are immutable at that SHA. The 2022 replication wiki and 2016 List@Level introduction describe their historical scope; they are not proof that every present-day node behaves identically.[11][12]

The pinned sample separates Nodes/Connectors/View and stores stable port IDs, Replication, Level/UseLevels/KeepListStructure. PortModel identifies ports uniquely within a graph; serialization converters copy level/default settings and restore connectors against ports.[2][3][9] Those are design precedents, not a reason to reuse Dynamo's .NET type names or infer missing semantics.

## 2. Replication profile `dynamo-evidence-v1`

### 2.1 Established lowering and ordering

For nodes using `NodeModel.UseLevelAndReplicationGuide`, enabled port level `n` lowers to negative engine at-level `-n`, with KeepListStructure passed as the dominant flag. **Auto is not an alias for Shortest:** Auto appends guide `<1>` only to ports with levels enabled; Shortest appends `<1>` to every argument; Longest appends `<1L>` to every argument; CrossProduct appends `<1>`, `<2>`, … in input-port order. Auto without levels appends no guides and leaves rank dispatch to the VM. This is the exact scope of NodeModel lines 1641–1689; node overrides may differ.[1]

Guides process left-to-right levels, ascending guide number within each level: shared numbers zip, unique numbers form Cartesian loops, outer loop from the earlier sorted guide. Scalars are promoted for enforced guide iteration. Guides precede remaining rank replication. Default zip truncates to shortest; `L` repeats the last item of a shorter nonempty argument. Pinned Replicator lines 67–83 select longest when any matching guide requests it.[5][11]

List@Level selection is not generic recursive mapping: pinned AtLevelHandler computes maximum depth, promotes when needed, extracts at the selected depth and records indices for a dominant argument. It can restore only **one** dominant input structure. If multiple effective dominant arguments occur, lines 195–198 log `MoreThanOneDominantList` and return no dominant structure; do not invent a winning port. Restoration is conditional on outermost replication including the dominant argument (lines 206–246).[4] The introductory UI description likewise permits only one kept input structure.[12]

Pinned `ComputeReducedParams` also asserts the first zipped pair from `[1,2]` and `[3,4]` is `(1,3)`; it is a reduction-unit test, not an end-to-end Auto oracle.[6]

### 2.2 Supported subset and unresolved gates

Node signatures MUST declare parameter scalar/list rank (`0`, fixed positive integer, or `any`) and nullability. The initial evaluable subset is the concrete signatures/calls in the fixture table below: scalar addition, arbitrary-rank identity at tested levels, and rank-one Sum with the tested dominant level. Scalar/list promotion is established only for the cited calls, not every overload. Stable port `index` defines argument order; parallel scheduling MUST NOT reorder output lists.

The pipeline for supported calls MUST mirror Dynamo: attach levels and lacing guides per NodeModel; transform at-level arguments and retain dominant indices; enforce guide loops; resolve residual rank calls; conditionally restore dominant shape. Pinned Executive lines 799–800 and 926–933 apply at-level transformation before JILDispatch; CallSite lines 1346–1379 perform guide demotion/instruction construction, endpoint resolution, execution and conditional structure restoration.[13][14] Scalar guide promotion described in the historical wiki is therefore not a substitute for source-level demotion/dispatch in unsupported cases. The general VM dispatch/overload/promotion algorithm is **not yet fully established** by this research. Unsupported rank/signature combinations MUST report `UNRESOLVED_REPLICATION_PROFILE` before evaluation/model proposal, not approximate zip or flatten silently.

Per-call explicit guides are saved as ordered sequences per argument, including signed integer guide values and longest flags. The wiki establishes guide ordering, not how an ordinary node's generated lacing guides should combine with an authored explicit guide. Therefore `guide_source` is `lacing` or `explicit`: mixed generated/explicit guide execution is gated pending a pinned Dynamo call-site fixture. This is an OpenBIM support restriction, not a claim that Dynamo refuses the combination. Explicit guide-only cases in the corpus use Auto with levels disabled, so no generated guides conflict.

**Unresolved/gated before AUTO-004 may claim full replication completion:** jagged ranks beyond cited level fixtures; empty zip/Cartesian/Longest inputs; null values and null/type overloads; disabled-lacing node overrides; multiple kept structures' complete values/warnings through UI; mixed levels + explicit guides + rank promotion; multi-output node shape; dictionary replication. No expected Dynamo value is guessed for these. Save/inspect such settings losslessly, mark unsupported, refuse run. Add pinned source/test evidence and exact output/warning fixtures, then independent review, before enabling each case. The current gate does not authorize replacing Dynamo behavior with new semantics.

## 3. Proposals, dependency groups and managed outputs (own policy)

### 3.1 Pending identity and partial application

- Pending handle is `{run_id, proposal_id, local_id, element_type}`. It is not an IFC GlobalId or persistent model ID. Reject cross-run/cross-proposal, cancelled, unresolved and wrong-type handles before apply. A downstream operation referring to a pending host MUST have an explicit dependency edge.
- Compute connected dependency components for operations that require co-commit, including host/dependent creations and rule-5 all-or-nothing route/fittings. Merge overlapping components transitively. A successful group resolves its local handles to persistent IDs inside the same atomic transaction; none escape before commit. Independent groups may apply separately; operation ordering within a group is topological.
- A stale prerequisite rejects its whole group as `stale` (re-evaluate/review required). A locked member turns the **whole group** into a change request with unresolved handles kept only as request-local descriptors, not project ownership. Other independent groups may apply. An unlocked concurrent write follows rule 5 last-writer-wins only after stale reads are valid; preserve/flag the losing edit. Report applied groups/elements, flagged conflicts, requested groups and stale/rejected groups separately.
- Ownership-map changes and model operations are atomic per successful group only. Failed/requested groups MUST NOT advance ownership or allocate committed IDs. One undo entry includes successful groups and their ownership mappings, with explicit request-log references; undo restores both model and mappings together. Undo must obey current collaboration preconditions, never silently overwrite later edits. Requests remain audit records; undo issues a linked withdrawal rather than erasing history.
- Cancelled/incomplete evaluation has no committable proposal. Its partial previews are diagnostic; invalidate all handles. Cancellation during apply finishes or rolls back the current atomic group; stop before further groups and record the already-applied subset for undo. No retry of old pending handles: create a new run/proposal and review.

### 3.2 Ownership and identity policies

Project op log owns mappings keyed by `(model_id, graph_id, node_id, output_port_id, output_key)`, recording element ID/IFC GlobalId, creating run, latest applied run, graph revision and history. Graph JSON carries policy only, never this map. Stable external row keys (e.g. inspection-record ID) plus an output slot key are preferred. Missing/duplicate keys reject that node's proposal. Positional identity requires explicit opt-in with captured ordered input fingerprint; reorder then rejects until reviewed remapping, never silently reassigns A's element to B.

- `update_previous`: matching stable keys update the same element and retain its IFC GlobalId; incompatible replacement is a separately reviewed delete/create, not a silent ID change. Identical post-commit rerun proposes no changes, unless values or external/model dependencies changed.
- Reorder `stable_keys` leaves ownership unchanged and only changes preview ordering. Reorder `reject_changed_order` is mandatory for positional keys.
- Shrink `retain` is default: missing keys remain owned/in the model with an absent-output warning. `propose_delete` emits explicit deletions, subject to mandatory destructive review, dependency grouping, locks and undo. No implicit delete on list shortening.
- `always_create_new`: each confirmed run creates a new generation; never adopts/overwrites old output mappings. Record history under `(output_key, committed_run_id)`; retain prior generations. Switching back to update requires explicit selection/review of the generation to adopt.
- `detach`: propose removing selected ownership mappings only; retain model elements/GlobalIds. This mode emits no creates/updates and must not recreate missing detached outputs. Record tombstones to prevent later automatic re-adoption; explicit reviewed rebind is required. Policy changes alone never modify the model on graph open.

Required execution tests: host failure suppresses dependent and its mapping; independent group still applies; locked group becomes one request; wrong-run/type handle refused; cancellation cannot commit preview; mapping/model atomic rollback; undo/rerun; save/reopen mapping recovery; stable-key A/B reorder retains IDs; duplicate-key rejection; shrink retain/delete; detach then rerun; two create-new generations retained; switch-back requires reviewed selection. All destructive proposals are reviewed even for trusted code and Player.

## 4. Cache and stale validation (own conservative policy)

Cache key includes engine/replication profile/library/client API versions, node implementation and executable graph definition digest, typed input values, **model identity + snapshot generation for host and every linked model in scope**, ownership-map generation for managed nodes, and identities of captured external resources. Global model IDs prevent reuse across projects with coincident revision numbers. Snapshot generation changes on insertion, deletion or change, so an empty collection cannot stay cached after insertion. Captured CSV bytes are immutable per run; key by canonical authorized resource identity + content digest, not pathname/mtime alone. Resource capture failures refuse evaluation.

Only registry-declared pure nodes using captured inputs are eligible. Ordinary arbitrary Python, network, clock, random or undeclared external reads are nonpure/uncached; their dependent results are also ineligible. A pinned environment does not make arbitrary Python pure. A future audited pure implementation requires explicit effect/dependency proof, not a user checkbox. Do not cache run-local pending handles or entire mutation proposals: cache immutable pure values/read records and instantiate a fresh run/proposal.

Cache hit restores the full dependency/read record for commit checks, including negative collection reads and external identities. Commit validates element reads per group; collection/negative reads conservatively validate all involved snapshot generations. Resource content and ownership generation changes invalidate affected proposals. This may invalidate after unrelated model changes; that conservative cost is accepted. It is not a whole-document veto on independent element-only groups.

Finer invalidation is **gated** until exact collection/index predicate dependencies (including empty results, insertion, deletion, filter edits, linked-model scope), external resource versioning and cache-hit dependency restoration have tests. Fixed output order is not evidence of purity or correct invalidation.

Required cache-on versus forced-full equality: same snapshot + captured resources + settings; insertion into empty collector; matching deletion/filter change; linked-model insertion; CSV bytes changed at same path; declared resource change; model A/B same generation; dependency/library/API change. Compare canonical values/proposals after normalizing run-local IDs only. Separately test post-commit `update_previous` no-op/retained IDs against the **new** snapshot. Never assert identical creation proposals before and after committing.

## 5. Trust, Python and MCP (own security boundary)

Arbitrary CPython is **trusted local code executing with the user's OS rights**. Worker processes and a virtual environment provide fault/dependency isolation, **not an OS security sandbox**. Direct Python imports can access files/network/processes independently of model token scopes. UI MUST explicitly warn there is no filesystem/network confinement. Restricted or untrusted policy MUST NOT execute arbitrary Python, imports or package build hooks; require separate informed trusted-code approval or refuse the run. Do not label a read-only-model graph safe for the filesystem.

The app continues enforcing model-scoped, expiring tokens: read-only by default, own-model proposals only with granted scope, linked models read-only. Tokens cannot grant more than caller authority. The supported model path is the `openbim` client, not a claim to confine malicious code running as the user. Brokered non-Python file/network nodes enforce separately authorized paths/endpoints; untrusted native/plugin code is likewise not implicitly allowed.

Approval binds graph executable digest, all reachable subgraph/code bytes, Python engine/ABI/client API versions, dependency lock and environment identity, permissions, model identity and captured resource/input digests. Any executable/policy/dependency/code change invalidates code/run/proposal approvals; view-only moves do not. Model snapshot/read dependency change invalidates the proposal as above. Folder trust/signature is provenance only, not execution or commit consent. A graph stores required trust policy, **never an approval token**.

Python environment: exact engine build/ABI, versioned client API, isolated per-lock virtual environment, locked transitive wheel artifacts with SHA-256 and source origin; installation requires a separate informed prompt listing artifacts/origins and the fact installed code executes with user rights. No automatic installation, imports, script execution or graph opening side effects on open/inspect/source-read. Default refuse unpinned dependencies, source distributions/build hooks and hash mismatch. An unavailable wheel blocks the run rather than running a build. Installing/upgrading/repairing artifacts requires new consent. Denial leaves graph inspectable and run blocked. Verify installed lock/environment identity before each approved execution.

MCP capabilities are separate and default denied except metadata inspection: `graph.inspect` (redacted metadata), `graph.source.read` (code/source disclosure), `graph.edit` (non-code source diff), `graph.code.edit` (Python/Code Block/dependency edits), `graph.run` (evaluation only). Code-bearing edits require both edit capabilities, user diff acceptance, then fresh trusted-code approval; adding a requirement cannot escalate into install authority. `graph.run` never authorizes model commit or package installation. Saved graph/source reads and writes require canonical authorized paths with symlink/reparse resolution and TOCTOU-safe open; embedded subgraphs/resources use the same checks. `run_from_json` requires the same source/code/run approvals, not a path bypass. Outputs/logs may expose file/model data and are permission-filtered.

Human model approval is per run/proposal digest and current executable/input/resource/model state; destructive proposals show deletes/replacements/ownership detach explicitly. MCP cannot self-confirm. Headless without an interactive approval channel produces a proposal only. Test denied install; open/inspect has no side effects; restricted Python refused **before** worker/import; trusted warning states direct file/network access is possible (no denial test is falsely promised); direct model call denied by scope; source disclosure/path denied; AI adds code/dependencies then old trust fails; revision change after review refuses commit; Player cannot persist auto-apply.

## 6. Serialization v1 (own schema, Dynamo-informed)

Representative round-trip fixture: [graph-v1.json](fixtures/graph-v1.json). It deliberately includes a gated combination (levels plus explicit guides) to prove lossless inspect/save, **not permission to run it**. A serializer MUST not drop settings merely because the current engine cannot evaluate them. This is not a Dynamo `.dyn` file. Stable IDs, connectors and port-level settings follow the source precedents; quantity/managed-output/security fields and canonical bytes are OpenBIM-specific policies.[2][3][9]

### 6.1 Fields and invariants

- Top level: `schema_version:1`, stable `id`, name/description/doc_url; `replication_profile`; exact `dependencies[]` entries `{id,version,artifact_sha256}`; `nodes[]`, `connectors[]`, `inputs[]`, `outputs[]`; `python` (`null` or engine/build/ABI/client_api/environment_lock); `extensions.openbim` for permissions/trust/cache; `view` for presentation only. Digests are lowercase 64-hex SHA-256 over named artifact bytes; fixture values are synthetic format examples, not installable packages.
- IDs are opaque nonempty strings, stable across save/load, rename, reorder and layout edits. Graph/node/port/connector/interface IDs have their own unique namespaces; port IDs are graph-wide unique. Production creators use UUIDs; examples use readable tokens. Duplicate or dangling IDs reject load-as-executable. Changing a node definition migrates ports explicitly, never by localized label or incidental array position.
- Node: `id`, exact `type` (`lib@version::name`), `parameters` typed object, `lacing` (`Auto|Shortest|Longest|CrossProduct|Disabled`), `frozen`, `ports[]`. Each port has `id`, `index`, `direction`, `type`, `rank`, `nullable`, `level`, `use_levels`, `keep_structure`, `using_default`, typed `default`. Output ports store levels disabled. An optional per-call `call` holds `guide_source` and `arguments[]` `{port_id,guides:[{value,longest}]}`; guides are ordered outer-to-inner. No implicit merge of explicit and generated guides.
- Level is positive integer; inactive default is 2 as in pinned PortModel constructors. `keep_structure` requires `use_levels`; selecting a kept port should clear the prior kept port in UI. Imported multi-keep settings are preserved with diagnostic/run gate, not silently assigned a winner.[2][4]
- Connector: `id`, `start:{node_id,port_id}`, `end:{node_id,port_id}`; start MUST be output, end input, types/ranks must be validated; at most one incoming wire per input. Connector visibility/reroute points live in view, not endpoint identity. Cycles require an explicitly supported future construct; v1 rejects them before run.
- Interface: `id`, explicit `binding:{node_id,port_id}`, `order`, type/rank/nullability, `unit` (`null` when not quantity), typed default/min/max/step, `label:{en,fr}`. Inputs bind input ports, outputs bind output ports; no duplicate input binding. Defaults/ranges must match target type/dimension. Two same-typed Player inputs remain distinct by ID/binding, not label. `order` is unique within inputs/outputs.
- `extensions.openbim` is the explicit namespace for **non-Dynamo** behavior. Graph fields: `permissions:{model,files,network,graph_capabilities}`, `trust:{python_policy,code_approval,install_approval,commit_confirmation}`, `cache:{mode,python,network}`. File grants are canonical path/mode records, network grants explicit endpoint records (empty arrays deny brokered access); graph_capabilities is the requested distinct capability list. Requests are not grants. `model` is `read_only|propose_own_model`; no linked writes. Policy strings are closed enums shown in the fixture.
- Creating node `extensions.openbim.managed_output`: `mode` (`update_previous|always_create_new|detach`), `identity:{kind,key_fields,output_slot}` (`external_key` or explicit `position`), `reorder` (`stable_keys|reject_changed_order`), `shrink` (`retain|propose_delete`), `detach` (`retain_elements_tombstone`), `create_new` (`retain_generations`), `adopt_generation` (`null` or selected committed run ID subject to reviewed rebind). Project mappings/run handles never go here. These fields implement §3, not Dynamo element binding.
- Python node parameters hold source code and Python header reference; header MUST contain engine/version/build/ABI/client API and full artifact lock with each transitive wheel's name/version/origin/SHA-256. Environment lock records its digest and isolation type. The code approval and install consent records are outside graph JSON. Restricted policy can persist Python source but never execute it.
- View: keyed node positions/preview flags, groups/notes/reroutes and Run mode `Manual|Automatic`. No Periodic. Layout cannot alter executable identity; run mode triggers evaluation only, never commit. Sidecar thumbnails only; no binary embeddings or project binding data.

### 6.2 Values, canonical bytes and migration

Scalar values are tagged where ambiguous: a quantity is `{"kind":"quantity","si":"6","dimension":[1,0,-1,0,0,0,0],"display_unit":"m/s"}`. Dimension exponent order is length, mass, time, current, temperature, amount, luminous intensity; seven integer exponents required. `si` is normalized decimal string in SI (no exponent, no plus, no trailing fractional zeroes; negative zero becomes `0`). Display unit is presentation only and must match dimension. Booleans/strings/lists/dictionaries are JSON-native; null is permitted only at nullable ports/optional fields, never conflated with missing/default. JSON non-finite numbers are rejected, not encoded as strings/null; diagnostics are separate. Numeric constraints and ordinary dimensionless numbers are finite IEEE-754 binary64; integers outside exact binary64 range must be explicitly typed decimal strings or rejected. SI decimals use decimal-string normalization, not binary64 rounding.

**Canonicalization is an OpenBIM policy, not a Dynamo feature.** UTF-8 without BOM, LF, final newline, two-space indent; object keys sorted by Unicode scalar value, unescaped Unicode except mandatory JSON escapes. JSON numbers use shortest round-trip binary64 decimal, lowercase `e`, no plus/leading exponent zeroes, `-0` to `0`, integral exact numbers emit integer spelling. Semantically unordered ID-bearing arrays (nodes/connectors/interfaces/dependencies) sort by `id`; ports sort by `direction` (input before output), then explicit direction-local `index` (unique per direction), call arguments by referenced input port index. `view` ID collections sort by `id`. List values, guides, dimension vectors, ordered key_fields, wheel dependency execution-independent metadata lists unless declared unordered, and authored ordered group membership MUST retain order; canonicalization cannot change executable meaning. Wheel artifact records sort by name/version/origin; path grants/endpoint grants sort by their canonical path/endpoint. Fixture validator exercises the fixture's numeric subset; edge binary64 formatting requires cross-language vectors before production serializer completion.

Unknown schema version: inspect raw JSON read-only with diagnostic, no evaluation/write-back/migration without explicit request. For schema v1 unknown executable fields, extension namespaces, library versions, replication profile or enum values: preserve raw bytes for inspection/export, refuse evaluation/canonical rewrite until understood. Never silently ignore potential executable settings. Explicit migration names source/target versions, reports field/ID/policy changes, produces a new file after user approval and backup; invalidates all execution/install/proposal approvals. No auto-migration on open. Unknown presentation fields may be preserved losslessly but are excluded from executable digest only after registered as presentation-only.

Required serialization acceptance: canonical serialize→parse→serialize byte identity; perturb unordered array/object order and recover canonical bytes; preserve list/guide order; same-typed inputs preserve distinct bindings; modes/guides/levels/Python API survive reopen; layout edits leave executable digest unchanged; code/policy/dependency changes alter it; duplicate IDs/dangling or reversed connector/type mismatch rejected; unknown version/field no execution; quantity/null/non-finite/large-integer cases; explicit migration invalidates approvals. No full schema/engine conformance claim follows from the documentation fixture validator alone.
